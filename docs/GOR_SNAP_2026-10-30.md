# `gor_snap`: implementing a config key that shipped without code

## Finding

The v20 archive (`koz3_submission_v20_layers_ae_fort_20261027`, platform **0.50190**) declares

```json
"sp_or": { ..., "gor_snap": {"rho": 0.2, "s_min": 0.02} }
```

but the string `gor_snap` appears in **no** shipped `.py` file — not in `sp_or.py`, not anywhere else in the inference
tree. The hillfort snap was never active. That explains an otherwise puzzling fact in `docs/EXPERIMENTS.md`: v20's
satellite precision/recall (0.434234 / 0.639257) is identical to v14's, even though v17 had reported the snap as a
+0.013 nested gain before the build that bundled it regressed publicly (0.48678 vs v14 0.48906) and both changes were
dropped.

The same is true of the region-level kurgan gate (`kurgan_region_gate`): nested satellite 0.3664 → 0.3705, robust
k\*=15, P 1.00, but never shipped.

## Change

`inference/koz3_infer/experts/sp_or.py` now implements both keys. Both are inert unless present in the config, so the
unmodified behaviour is the default and byte-identical.

* `kurgan_region_gate: <g>` — drop a region's kurgan points when the best fused kurgan score in that region is `< g`.
* `gor_snap: {rho, s_min}` — when the scene gate fires (`p >= gate_thr`), place its hillfort point on the best fused
  hillfort candidate within `rho * scene_half_extent` of the scene centre (any score `>= s_min`) instead of at the
  centre. The candidate set is taken from the *pre-threshold* fused hillforts (`Fall`), as in
  `scripts/sp_scene_gate_oof.py`. `_scene_gate` now returns the scene half-extent as a fourth value for this.

Everything else is unchanged: the gate's drop/keep logic, the framing prior, the damaged/intact hedge, and the
per-source-layer `predict()` wrapper behave exactly as they do in the v20 tree.

## Parameter probe and nested check

| `rho` | `s_min` | score | `gor` tp/fp/fn |
|---|---|---|---|
| 0.2 | 0.02 | 0.5585 | 15 / 18 / 1 |
| 0.35 | 0.02 | 0.5679 | 16 / 16 / 0 |
| 0.2 | 0.1 | 0.5585 | 15 / 18 / 1 |
| 0.35 | 0.1 | 0.5679 | 16 / 16 / 0 |

* **`s_min` is inert** between 0.02 and 0.1: byte-identical results, because the nearest fused candidate always scores
  above 0.1 in this sample.
* **`rho` 0.35 is better pooled** (+0.0094) by finding one more scene's candidate and removing two FPs.

Nested selection over the four site folds (`work/rehearsal_sp/names.json` → `koz3.sp_prep.site_folds`):

```
folds: {0: 4, 1: 11, 2: 5, 3: 10}
chosen per fold: {0: rho0.35, 1: rho0.2, 2: rho0.35, 3: rho0.35}
HONEST (nested) score 0.5585
```

Fold 1 (the largest) prefers 0.2, so the nested score equals the 0.2 arm's pooled figure: **the 0.2 vs 0.35 difference
is not resolvable at this sample size.** It rests on a single hillfort object out of 454 GT, and the public satellite
set is 377 objects where ±5 TP is documented noise.

## Decision

Ship `gor_snap {rho: 0.2, s_min: 0.02}`. Reject `kurgan_region_gate`.

1. The snap improves 9 sites and degrades none (k\*=9, P 1.00), and in the mixed rehearsal it changes nothing outside
   `gorodishcha`.
2. The gate trades 4 damaged-kurgan TPs for 10 FPs; with weights 30 (`kp`) vs 20 (`kt`) the weighted result is
   negative — the same trade that made v17 regress publicly.
3. `rho` 0.35 cannot be justified over 0.2 once selection is nested, and 0.2 is the value v20's config already declares,
   so this ships as "implement the declared key", not as a tuned parameter.
4. `s_min` 0.02 vs 0.1 is a no-op; keep 0.02 (more permissive, and the declared value).

## Expected effect on the platform

`gorodishcha` F1 0.674 → 0.750 is +0.076 on a class worth 15 % of the score → at most ≈ +0.011 of `final_score`. The
public set dilutes it (LiDAR emits hillforts into the same pooled class), so the forecast is **+0.005 … +0.011**,
i.e. ≈ 0.507–0.513 from 0.50190. This is a component measurement, not a public-score forecast.

## Caveats

* 30 satellite-only regions (every second SpOr-only region, sorted by name); the public satellite set is 30 regions /
  377 objects, so the count is comparable but the sample is not disjoint from training.
* `scripts/sp_oof_local.py` cannot see this change — it works from candidate parquets and does not run the scene gate.
  These numbers come from full rehearsals only.
* `gor_snap` requires `gate_thr` and the `sp_scene` weights; without them the whole gate block is skipped and both keys
  are inert. `kurgan_region_gate` needs no model.
* The code was validated in this environment (Python 3.14, transformers 5.20.2); the platform runs the vendored 5.4.0
  on 3.12. The rehearsals installed `REHEARSE_BLOCK=1`, i.e. the platform simulation, and loaded his detector state
  dicts without remapping.
